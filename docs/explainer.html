Your agent holds a key.
It does not hold authority.

Tollgate moves an AI agent's spending limit off the prompt and into a contract the agent cannot change. It can request a payment. Only the chain can approve one.

The payment path

The detail that matters is where the money goes, and it is not where people assume.

Where a payment can end up

Four outcomes. Three are clean answers. One is genuinely hard, and it is the one most systems get wrong.

Refused before sending

nothing moved

The agent pre-checks with a free read. Costs no gas and no transaction. Three of four services in the demo end here.

Refused on chain

nothing moved

Mined and reverted with a reason code. Gas is spent, no money is. Policy changed between the check and the execution.

Settled

money moved

A Spent event, a receipt, and a row in the audit log keyed on transaction hash so a reorg cannot double-count it.

Unresolved

unknown

Submitted, no receipt in time. It may still land. The only wrong move is to retry, which is how one invoice gets paid twice.

A timeout is not proof of failure. The agent is told so in those words, because a model handed a raw stack trace will do the reasonable-looking thing and try again.

And if it ever did double-pay, the caps still hold — the budget, the per-payment ceiling and the velocity bucket all apply to the second payment exactly as to the first. A double payment is a bookkeeping bug, not a failure of the leash.

Micro-payments

Measured on chain, not estimated. Gas is flat at about $0.002 per payment whatever the amount, so the only thing that changes with size is the overhead ratio.

PaymentFee overheadVerdict
$2.000.10%negligible
$0.500.40%comfortable
$0.201.0%the break-even most would accept
$0.102.0%workable — verified with a real payment
$0.054.0%marginal
$0.0120%don't

The contract itself has no minimum — it accepts down to one unit, $0.000001, and rejects only zero. The floor is economic, not technical. Below roughly $0.05 the answer is batching or off-chain settlement, not a smaller payment.

Why each piece is there

Choices specific to this problem. Where a default would have been fine, it isn't listed.

ChoiceWhy this one
ArcGas is USDC. An agent economy prices work in dollars; needing a volatile gas token to buy a $0.05 API call is a currency problem before it is a spending problem.
Allowance, not custodyWe never hold funds. A vault would mean a far larger blast radius and a much harder thing to trust in a weekend-old contract.
Solidity 0.8.28Transient storage — a reentrancy guard at ~100 gas instead of ~5,000.
FoundryFuzzing and invariants are native. For a contract whose value is "this limit always holds," the invariant is the test that matters.
One _evaluateThe pre-flight view and the enforcement path share one implementation, so they cannot drift.
viem + Node 26Types inferred from the ABI, and no build step. In a codebase where every amount is a bigint, the compiler catches decimals errors that users would otherwise find.
Server components, no APIThe page reads the chain directly. No route handlers, no client fetching, no serialisation boundary to keep in sync.
No databaseThe audit log is rebuilt from events every request, so it cannot drift from what happened and cannot be tampered with. Losing the server loses nothing.
No chart library or webfontsAnything that has to load is something that can fail to load, in front of a judge, on conference wifi.
Deliberately unrestricted toolsThe agent can call pay_address with any address and any amount. Narrow tools would be the app-level guardrail this replaces — if the demo only worked because the tools were restrictive, it would prove nothing.

What isn't built

The parts worth knowing about before anyone asks. The full list is in the repository.

Gaps in the claim

  • The dashboard cannot show a refusal. Reverts emit no events, so the UI proves what was allowed and cannot display what was stopped — the product's central claim.
  • The attack demo depends on a model's choices. The hard evidence is two contract refusals; the model's own reasoning is not evidence. A scripted adversary would fix this.
  • The owner key sits in a .env file. Non-custodial in the contract, custodial in the demo app.

Not yet capable of

  • One agent per owner. A real operator runs a fleet.
  • Per-payee budgets and time windows. The allowlist is binary today.
  • Editing caps in the UI. Only pause and payee approval are writable.
  • Batching. The fix for flat gas making sub-$0.05 payments uneconomic.
  • An audit. Reviewed by us and a fuzzer, nobody else.

One known footgun, documented rather than quietly carried: nothing stops an owner from allowlisting the PolicyEngine itself, which has no withdraw function. A one-line fix, not applied before submission because redeploying would invalidate the verified contract and every proof link in the demo.

PolicyEngine is deployed and verified at 0x7Fa88da4FD0a86Af9c9567f0c317be6FBa1a376D on Arc testnet. 40 tests, including fuzz and invariant suites. Every payment shown in the dashboard links to its transaction on ArcScan — the page is meant to be checked, not trusted.
