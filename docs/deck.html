An on-chain enforcement layer for autonomous agent spending, built on Arc. Non-custodial, verifiable, and binding on a key that has already been stolen.

01 — The problem

Every guardrail people build lives inside the agent.

In the prompt. In the tool definitions. In the app that calls the model. All of it shares one flaw: it assumes the agent is the thing enforcing the rule.

Prompt injection

Instructions arrive in the data the agent was asked to read.

A leaked key

The attacker skips the agent entirely and signs directly.

A retry loop

No malice required. A bug spends the budget just as fast.

Each one routes around a check that lives in the same process as the thing being checked.

02 — The claim
An agent whose key has been fully compromised still cannot spend outside its policy.

That sentence is falsifiable, which is the point of stating it that way. It fails if there is any path from the agent's signing key to a USDC transfer that does not pass through policy evaluation.

So the architecture is mostly an argument that no such path exists — and the demo is an attempt to find one, on camera, with the real key.

03 — How it works

The constraint sits where the agent cannot reach it.

Owner (own wallet) Agent (session key) │ │ │ approve(PolicyEngine, budget) │ trySpend(payee, amount) ▼ ▼ ┌──────────────────────────────────────────────────┐ │ PolicyEngine │ │ budget · per-payment · token bucket │ │ payee allowlist · expiry · pause │ └──────────┬─────────────────────┬─────────────────┘ │ OK │ anything else ▼ ▼ transferFrom(owner → payee) emit Refused(reason) emit Spent(...) nothing moves

Money moves owner to payee. It never enters Tollgate — there is no vault, no pool, and no withdraw function to write a bug in.

The owner grants an ERC-20 allowance sized to the budget, so the allowance is a second ceiling that holds even if our contract is wrong. Revocation is approve(0): the owner leaves without our permission or our servers being up.

06 — Feedback on Circle's stack

Six findings, from building rather than reading.

  • Modular Wallets session keys are unreleased, so the ERC-6900 module we intended to build has no deployment path. We designed the allowance model instead — and it turned out to work on any EOA, on any ERC-20 chain, with no account abstraction at all.
  • Paymaster does not support Arc, and on Arc it is not needed — USDC is already the gas token. The product that fills the gap is Gas Station, which is a different thing with a similar name.
  • The Agent Stack starter kit is Base-mainnet-only by its own .env.example, on a hackathon whose premise is Arc.
  • Gateway nanopayments settle off-chain, so on-chain policy cannot intercept them. Our enforcement point is the top-up. Circle's own controls are genuinely stronger here, and we would rather say so.
  • The "Arc rejects PUSH0, compile to paris" advice is obsolete. We disassembled Circle's own live ERC-8183 proxy and found ten PUSH0 opcodes in its executed fallback.
  • eth_estimateGas leaves under 1% of headroom on a USDC transfer — 97,846 returned against 96,931 actually consumed. Payments fail intermittently with no readable reason. We buffer 30%.
07 — What we would push back on

Where the claim is still stronger than the evidence.

Stated here rather than left for someone to find, because a submission that only lists strengths is marketing.

The model chose not to attack

It also declined on its own reasoning. That is not the evidence — the two contract refusals are. A deterministic attacker script would make the guarantee reproducible rather than anecdotal.

One policy per owner

A real operator runs a fleet. Today "an operator's agents" is one agent, and multiple policies are the next contract change.

Nothing is hosted

It runs on a laptop against testnet. Arc mainnet is not live, and we do not imply otherwise anywhere.

No external audit

Reviewed by us and a fuzzer. Invariant and differential suites pass; a prover and an auditor would settle it. Hard gate before mainnet.

08 — Why this matters

The leash has to survive the credential.

Circle already ships spend controls for agent wallets, and they are good. They are enforced off-chain, behind Circle's API, and they are in the path when the caller goes through Circle.

Tollgate's enforcement is in the contract: verifiable by anyone, portable across providers, and binding on a raw key with nobody in the loop. The two are complementary. Ours is the one that survives the credential being stolen.

Everything here is testnet. Everything shown is on a public chain you can check.
